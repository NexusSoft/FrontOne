# Módulo Recepción de Fruta (schema `Recepcion`)

> Parte de la memoria viva del proyecto FrontOne — ver [contexto.md](../contexto.md) para el índice completo. Reglas fundacionales viven en [arquitectura.md](arquitectura.md).

## Módulo "Recepción de Fruta" (schema `Recepcion`, nuevo — página de Ribbon propia junto a Acopio)

Proceso siguiente al de Acopio: cuando el camión regresa de campo a la empacadora, se pesa en báscula, se cuenta cajas y se registra contra una o varias Órdenes de Corte (`Acopio.OrdenCorte`) ya capturadas. El usuario mandó capturas de un sistema de referencia (listado + diálogo "Actualizar registro") que definieron los campos exactos; varias decisiones se aclararon vía preguntas antes de construir (ver detalle abajo).

**Decisiones de negocio confirmadas con el usuario:**
- El grid de líneas selecciona Órdenes de Corte **ya existentes** en FrontOne (picker), nunca captura libre — Huerta y "Cajas Cortadas" se traen automáticamente de la orden elegida (`Acopio.OrdenCorte.CajasEntregadas`, reetiquetado como "Cajas Cortadas" en este contexto porque esa tabla no tiene un campo separado con ese nombre).
- Una misma Orden de Corte **no puede usarse en dos Recepciones** — respaldado por `UNIQUE` en `Recepcion.RecepcionFrutaOrdenCorte.OrdenCorteId` (no solo validación de aplicación).
- Kilogramos por renglón: captura manual, no se reparte automáticamente del Peso Neto total.
- Cajas Entregadas/Cortadas/Recibidas Vacías del encabezado: captura manual **independiente** del grid (no es suma automática de las líneas).
- `PesoNeto = PesoBruto − PesoTara − TaraCajas − PesoMuestra` y `CajasDiferencia = CajasEntregadas − CajasCortadas − CajasRecibidasVacias`: ambos **calculados server-side** en `RecepcionFrutaService` (nunca se confía en lo que mande la UI, mismo criterio que `OrdenCorteService.ResolverYValidarAsync`) y también recalculados en vivo en la UI (`EditValueChanged`) para que el usuario los vea antes de guardar.
- `PesoProductor`: campo manual independiente (peso reportado por el productor, para comparar contra el peso real de báscula) — no se deriva de nada.
- `CoprefBico`: texto libre (código de inspección físico), sin catálogo.
- `NoLote`: ya tiene uso — ver [`contexto/lotes.md`](lotes.md). Se llena automáticamente con el Folio del Lote cuando la Recepción queda incluida en uno (`LoteService.AgregarLineaAsync`) y se limpia a `NULL` al quitarla o al borrar el Lote completo. El campo del form sigue en solo lectura (`_txtNoLote.Properties.ReadOnly = true`), pero ya no está deshabilitado "sin lógica" — la actualiza `Recepcion.sp_RecepcionFruta_ActualizarNoLote`, llamado desde el módulo Lotes, nunca por el propio form de Recepción.
- `CamionDestarado` (checkbox "¿El camión fue destarado?"): puramente informativo — el usuario aclaró que todos los datos (incluida báscula) se capturan juntos hasta que el camión ya terminó de descargar, no hay un flujo de dos pasos ni campos que se habiliten/deshabiliten según este check.
- "Capturar Nómina de Cortadores" (botón que aparecía en la referencia): **fuera de alcance** de esta iteración, no se construyó.
- Sin integración de báscula física — todo captura manual (`SpinEdit`).

**SQL** (`Database/Recepcion/`, primer schema de este módulo):
- `001_Schema_RecepcionFruta.sql`: `CREATE SCHEMA Recepcion`, `SEQUENCE Recepcion.SeqRecepcionFrutaFolio` (folio 7 dígitos, mismo patrón que Acopio), tabla `Recepcion.RecepcionFruta` (encabezado) y `Recepcion.RecepcionFrutaOrdenCorte` (detalle, `OrdenCorteId UNIQUE` + FK a `Acopio.OrdenCorte`, ambas FK sin `CASCADE` por regla dura del proyecto).
- `002_SP_RecepcionFruta.sql`: CRUD del encabezado. `sp_RecepcionFruta_Obtener` trae una columna `Huertas` con `STRING_AGG` de los nombres de huerta de todas las líneas de esa Recepción (una Recepción puede traer fruta de varias huertas) — se usa en la columna "Huerta" del listado. `sp_RecepcionFruta_Eliminar` borra primero el detalle y luego el encabezado dentro del mismo SP (sin `CASCADE`, control explícito).
- `003_SP_RecepcionFrutaOrdenCorte.sql`: CRUD del detalle — `Obtener` hace join a `Acopio.OrdenCorte`/`Catalogos.Huerta` para traer Folio/Huerta/CajasCortadas sin duplicarlos en la tabla de detalle. `Actualizar` solo permite cambiar `Kilogramos` (`OrdenCorteId` inmutable una vez creada la línea, mismo criterio que otros campos "de origen" del proyecto).
- `004_SP_OrdenCorte_DisponiblesParaRecepcion.sql`: **vive en schema `Acopio`, no `Recepcion`**, porque consulta `Acopio.OrdenCorte` — mismo criterio ya usado en el proyecto para SPs de un módulo que sirven a otro (ej. `sp_ListaPrecioFruta_ObtenerFechasPorProductorYRango` usado desde AcuerdoCorte). `sp_OrdenCorte_ObtenerTop100ParaRecepcion`/`sp_OrdenCorte_BuscarParaRecepcion` (mismo patrón Top100+Buscar que JefeAcopio) alimentan el picker de líneas, y `sp_OrdenCorte_EstaDisponibleParaRecepcion` valida antes de insertar una línea (respaldo del `UNIQUE`, para dar mensaje claro en vez del error crudo de SQL).
- `Database/Seguridad/022_Seed_Modulo_Recepcion.sql`: módulo `Recepcion` nuevo, pantalla `RecepcionesFruta`, permisos completos Administrador — clonado 1:1 del patrón de `015_Seed_Modulo_Acarreo_Zona.sql`.
- `Inicializar_Datos_Produccion.sql`: se agregaron `Recepcion.RecepcionFrutaOrdenCorte`/`Recepcion.RecepcionFruta` al arreglo `@Tablas` (detalle antes que encabezado) y el reinicio de `Recepcion.SeqRecepcionFrutaFolio`.

**Capas C#**: patrón estándar del proyecto — `RecepcionFruta`/`RecepcionFrutaOrdenCorte` entities, DTOs (`RecepcionFrutaDto` incluye `Huertas` para el listado), `IRecepcionFrutaRepository`/`RecepcionFrutaRepository`, `RecepcionFrutaService` (con auditoría completa Crear/Actualizar/Eliminar, módulo `"Recepcion"`). `IOrdenCorteRepository`/`OrdenCorteRepository` se extendieron con los 3 métodos del picker (`ObtenerTop100ParaRecepcionAsync`/`BuscarParaRecepcionAsync`/`EstaDisponibleParaRecepcionAsync`) — nueva entidad ligera `OrdenCorteDisponible`/`OrdenCorteDisponibleDto` para esa proyección.

**WinForms** (`FrontOne.WinForms/Forms/Recepcion/`, carpeta nueva):
- `RecepcionesFrutaForm` (listado, patrón `AcuerdosCorteForm`/`OrdenesCorteForm`): columnas Folio/No. de Lote/Fecha/Ticket/COPREF/Huerta/Peso Neto/Materia Seca/Chofer, `BestFitColumns`, Nuevo/Editar/Eliminar/Cerrar.
- `RecepcionFrutaEditarForm`: patrón "Form de alta/edición" con dos `GroupControl` (Control de Báscula, Control de Cajas), `PesoNeto`/`CajasDiferencia` como `SpinEdit` de solo lectura recalculados en vivo (`EditValueChanged` de los campos que los componen), grid de detalle **bindeado a un `BindingList<FilaDetalleRecepcion>` en memoria** (clase mutable nueva, patrón ya usado en `ListaPrecioAcarreoForm` para grids editables) — el detalle **no se persiste hasta el Guardar del encabezado**: en modo Nuevo se inserta todo junto tras crear el header; en modo Editar se aplican altas/bajas/cambios de línea (`_idsEliminados` trackea borrados) también al hacer clic en Guardar, no antes. Decisión de diseño para evitar manejar un header "borrador" a medio guardar.
- `RecepcionFrutaDetalleEditarForm`: diálogo chico para agregar/editar una línea del grid — **no toca la base de datos**, es puramente de captura (picker de Orden de Corte + Kilogramos), el padre decide cuándo persistir. En modo edición de una línea ya agregada, el picker de Orden de Corte se deshabilita (inmutable).
- `SeleccionarOrdenCorteForm`: picker nuevo (patrón `ProductoresForm`/`BuscarListaPrecioFrutaForm`) — TOP 100 al abrir + búsqueda por Folio/Huerta (mínimo 2 caracteres), solo muestra Órdenes de Corte disponibles (no usadas en otra Recepción).

**Ribbon**: nueva `RibbonPage _pageRecepcion` ("Recepción"), agregada junto a `_pageAcopio` en `_ribbon.Pages.AddRange` — pedido explícito del usuario ("al lado de Acopio"). Contiene un solo grupo `_grpRecepcionFruta` ("Recepción de Fruta") con el botón `_btnRecepcionesFruta` (`Id=26`, `MaxItemId` 25→26), abierto con `ShowDialog` (patrón modal simple, no MDI). Permiso `ModuloRecepcion = "Recepcion"` / pantalla `"RecepcionesFruta"`.

### Iteración: solo una Orden de Corte por Recepción; Cajas Entregadas y Kilogramos ya no se capturan a mano

El usuario probó la pantalla y pidió dos ajustes sobre el diseño original (que permitía varias líneas con Kilogramos manual por renglón):

- **Solo una Orden de Corte por Recepción** (antes se permitían varias, con "Huertas" concatenada en el listado): `BtnDetalleNuevo_Click` en `RecepcionFrutaEditarForm` ahora rechaza agregar una segunda línea si `_filas.Count > 0` ("Quita la actual antes de agregar otra"). No se tocó el modelo de datos (la tabla de detalle sigue soportando 1:N por si se relaja la regla después), es una restricción de UI.
- **Cajas Entregadas del encabezado ya no se captura a mano**: `_spnCajasEntregadas` pasó a `Properties.ReadOnly = true` y se llena automáticamente con `Acopio.OrdenCorte.CajasEntregadas` de la orden elegida al agregar la línea (y se limpia a `0` al quitarla).
- **Kilogramos de la línea ya no se captura a mano, es el Peso Neto del encabezado**: se quitó por completo el campo `Kilogramos` de `RecepcionFrutaDetalleEditarForm` (el diálogo ahora solo elige la Orden de Corte). Al agregar la línea, `Kilogramos = PesoNeto` actual; `RecalcularPesoNeto()` ahora también sincroniza `Kilogramos` de la fila del detalle cada vez que cambia algún peso de báscula (`_filas.ResetItem` para refrescar el grid).
- Como consecuencia, ya no hay nada editable por línea (Orden de Corte inmutable, Cajas Entregadas y Kilogramos automáticos) — se **eliminó el botón "Editar" del detalle** (`_btnDetalleEditar`/`BtnDetalleEditar_Click`), solo quedan Nuevo/Borrar.

Build 0 errores, tests 2/2. Sin cambios de SQL (los campos ya existían, solo cambió de dónde saca su valor la UI). UI sin probar en vivo (mismo caveat de siempre).

### Iteración: adjuntar foto/PDF del ticket de báscula ("Agregar Ticket de Pesada")

El usuario ya había probado la pantalla en Visual Studio (folio real `0000002` capturado) y pidió agregar la posibilidad de subir un archivo — la foto o PDF del ticket físico de báscula.

- **Almacenamiento**: se decidió guardar el archivo directo en la fila (`VARBINARY(MAX)` + nombre), no en disco/carpeta compartida — así la app no depende de que esa carpeta exista/esté accesible desde cada máquina que la corra. `Database/Recepcion/005_Alter_RecepcionFruta_TicketPesada.sql`: `ALTER TABLE Recepcion.RecepcionFruta ADD TicketPesadaArchivo VARBINARY(MAX) NULL, TicketPesadaNombreArchivo NVARCHAR(255) NULL` + los 3 SPs (`Obtener`/`Insertar`/`Actualizar`) regenerados con las columnas nuevas — mismo patrón que `007_Alter_TipoPago_NecesitaListaPrecios.sql`.
- **Auditoría**: el contenido binario **no** se serializa al log de auditoría (podría pesar varios MB por registro) — `RecepcionFrutaService` ahora tiene `SerializarParaAuditoria` (una proyección anónima sin el `byte[]`, solo un `bool TicketPesadaAdjunto` + el nombre del archivo) en vez de serializar la entidad completa.
- **UI** (`RecepcionFrutaEditarForm`, dentro del grupo "Control de Báscula" — se creció de 270 a 330px de alto para que quepa): botón `_btnTicketPesada` ("Agregar Ticket de Pesada" / cambia a "Reemplazar Ticket de Pesada" una vez que hay uno cargado) abre `OpenFileDialog` (filtro imágenes/PDF), lee el archivo a memoria (`File.ReadAllBytes`) — **no se sube a la BD hasta el Guardar del encabezado**, mismo criterio que el detalle. `_lblTicketPesadaArchivo` muestra el nombre del archivo ("Sin ticket adjunto" si no hay) y es clicable (cursor de mano) para abrirlo con el visor default de Windows (se escribe a un temporal en `Path.GetTempPath()` y `Process.Start` con `UseShellExecute = true`). `_btnQuitarTicketPesada` (solo visible si hay archivo) limpia la selección en memoria.

## Iteración: bloqueo visual de Recepciones tomadas por un Lote

El bloqueo de edición ya existía server-side (`RecepcionFrutaService.ActualizarAsync` rechaza con `ValidationException` si `ILoteRepository.RecepcionEstaEnLoteAsync` es verdadero — ver [`contexto/lotes.md`](lotes.md)), pero la UI no lo reflejaba: el formulario dejaba capturar y solo tronaba al guardar, y el listado no mostraba qué Recepciones estaban tomadas. El usuario pidió dos cosas explícitas:

- **`RecepcionFrutaEditarForm`**: si la Recepción abierta ya está en un Lote (`RecepcionFrutaDto.EstaEnLote`), se deshabilitan TODOS los campos capturables (fecha, chofer, placas, observaciones, básculas, cajas, camión destarado) y los botones que modifican estado (Ticket de Pesada, Nuevo/Borrar detalle, Guardar) — vía `AplicarBloqueoPorLote()`, llamado desde `CargarAsync()` al final. Se agregó un `LabelControl _lblBloqueado` (rojo, negritas, oculto por default) con el texto "Esta Recepción está en un Lote y no se puede editar. Quítala del Lote primero." — visible solo cuando aplica.
- **`RecepcionesFrutaForm` (listado)**: columna nueva "Bloqueo" que dibuja un ícono de candado en vez de texto/checkbox — candado rojo cerrado si `EstaEnLote = true`, candado verde abierto si `false`. Se implementó con `GridView.CustomDrawCell` (no hay precedente previo en el proyecto de una columna con ícono custom por fila): se detecta `e.Column.FieldName == "EstaEnLote"`, se pinta el fondo normal de la celda (`e.Appearance.FillRectangle`) y se dibuja el ícono centrado (`e.Cache.DrawImage`), con `e.Handled = true`. API de DevExpress (`RowCellCustomDrawEventArgs`, `AppearanceObject.FillRectangle`, `GraphicsCache.DrawImage`) verificada por reflection contra los DLLs instalados antes de escribir el código, mismo criterio que otras veces en el proyecto.

**Iconos nuevos** (`FrontOne.WinForms/Resources/Icons/candado_cerrado.png` / `candado_abierto.png`, 32×32, generados con `System.Drawing` — no existía ningún ícono de candado reutilizable en el proyecto para copiar como en el patrón habitual de `.resx`): candado rojo con grillete cerrado vs. candado verde con grillete abierto, mismo patrón de recurso embebido que `barcode.png` (`<EmbeddedResource Include="Resources\Icons\...">` en el `.csproj`, cargado en tiempo de ejecución vía `Assembly.GetManifestResourceStream`).

**Base de datos**: `Recepcion.sp_RecepcionFruta_Obtener` ganó la columna `EstaEnLote` (`EXISTS` contra `Lotes.LoteRecepcion` por cada fila) — mismo cálculo que `Lotes.sp_RecepcionFruta_EstaEnLote`, pero resuelto para todo el listado en una sola pasada en vez de un SP separado por Id. Esto crea una dependencia de `Recepcion` hacia el schema `Lotes` (dirección inversa a la habitual, donde el módulo más nuevo consulta al más viejo) — aceptado como pragmático dado que es de solo lectura y evita N llamados extra desde la UI.

**Capas C#**: `RecepcionFruta.EstaEnLote`/`RecepcionFrutaDto.EstaEnLote` (bool) nuevos; `RecepcionFrutaService.MapearDto` los propaga.

Verificado con `sqlcmd` contra `172.16.1.100\FrontOne` y con una prueba directa usando `RecepcionFrutaRepository.ObtenerAsync` (el mismo código que usa la app): las 8 Recepciones que ya tenían `NoLote` capturado por el módulo Lotes devuelven `EstaEnLote = true`, coincide 1:1 con la columna `NoLote`. Build 0 errores, `dotnet test` en verde. UI no se pudo probar visualmente en este entorno — pendiente que el usuario confirme que el candado se ve correcto y que los campos quedan realmente deshabilitados al abrir una Recepción bloqueada.

## Iteración: rename `CamionDestarado` → `DescargaCompleta`

El usuario pidió renombrar el campo (nota de la línea 18 de arriba, ahora desactualizada): "destarado" es el término técnico (pesar el camión vacío) pero no describe la acción real — lo que dispara el flag es que el camión terminó de descargar. Se preguntó al usuario el nombre exacto vía `AskUserQuestion`; eligió **"Descarga Completa"**.

Mismo criterio que el rename de `Lotes.Lote.Referencia` → `CodigoTrazabilidad` (`contexto/lotes.md`): `sp_rename` preserva los datos existentes (8 filas reales), nunca `DROP`+`ADD`. Detalle:

El mismo archivo redefine, consolidados, los 3 SPs (`Obtener`/`Insertar`/`Actualizar`) como última palabra — reemplaza a `011_SP_RecepcionFruta_CajasPerdidas.sql` (Obtener/Actualizar) y `012_SP_RecepcionFruta_Folio_Reutilizable.sql` (Insertar, folio `MAX+1`), combinando ambos + el rename en un solo lugar.

La regla de negocio (solo Recepciones con descarga completa entran a un Lote) no cambió, solo el nombre.
- **C#**: rename mecánico de `CamionDestarado` → `DescargaCompleta` en `RecepcionFruta`, `RecepcionFrutaDto`, `RecepcionFrutaReporteDto`, `RecepcionDisponibleParaLote`, `RecepcionFrutaRepository` (los nombres de propiedad de los objetos anónimos de Dapper deben coincidir exacto con los `@Parámetro` del SP), `RecepcionFrutaService`, `LoteService` (incluido el mensaje de validación, ahora *"todavía no tiene la descarga completa"*).
