## Qué es FrontOne

ERP para una empacadora/exportadora de aguacate. WinForms de escritorio (.NET 10), arquitectura en capas, SQL Server vía stored procedures (Dapper, sin EF Core), integración con SAP Business One Service Layer, UI 100% DevExpress 26.1.

Documento de arquitectura original: `Reglas/Arquitecto Senior .NET - Generación de ERP Empresarial.docx`.

## Arquitectura (capas)

```
FrontOne.Domain              Entidades, DTOs (records), interfaces de repositorio, enums
FrontOne.Application          Servicios de negocio (orquestan repos + validación + auditoría)
FrontOne.Infrastructure.SqlServer   Repositorios Dapper contra SQL Server (solo stored procedures)
FrontOne.Infrastructure.SapB1       Cliente del SAP Service Layer
FrontOne.Shared               Cross-cutting: Result/PagedResult, excepciones, CryptoService, Options, interfaces de seguridad
FrontOne.WinForms             UI (DevExpress), composition root (Program.cs + DI)
FrontOne.Tests                xUnit
```

Reglas de dependencia: `Application` no puede depender de `WinForms`. El puente para saber "qué usuario está haciendo esto" es `ICurrentUserProvider` (en `Shared/Security`), implementado por `SessionContext` en WinForms.

## Infraestructura / credenciales de desarrollo

- **SQL Server**: instancia `Lider-TI`, base `FrontOne`. Auth SQL (usuario `sa`, no Windows). Ejecutar scripts con `sqlcmd -S "Lider-TI" -d FrontOne -E -b -f 65001 -i archivo.sql` (el `-f 65001` es necesario para que los acentos no se corrompan).
- **SAP B1 Service Layer**: `https://fronterra.vdv.one:50000/b1s/v1`, compañía `TEST_PROD_FASA`, usuario `manager`.
- Ambas credenciales completas están en la memoria persistente de Claude (`sql_test_credentials.md`, `sap_test_credentials.md`), no se repiten aquí por seguridad.

### Mapa en `HuertaEditarForm` (dentro de `panelControl2`, tab "Información Adicional")
**Excepción documentada a la regla dura "UI 100% DevExpress"**: el control de mapa es `GMap.NET.WindowsForms.GMapControl` (paquete NuGet `GMap.NET.WindowsForms` 1.7.5 **únicamente** — no un objeto DevExpress). Es la única excepción en todo el proyecto — decidida y pedida explícitamente por el usuario después de que las tres opciones DevExpress-nativas fallaran en secuencia:
  1. `OpenStreetMapDataProvider` (`DevExpress.XtraMap`) — bloqueado con 403 "Access blocked" por `tile.openstreetmap.org` (no cumple su política de atribución/User-Agent, DevExpress no permite configurarlo).
  2. `BingMapDataProvider` — Microsoft **descontinuó Bing Maps el 30 de junio de 2025**; la clase compila pero está obsoleta y no funciona ni con API Key.
  3. `MapboxDataProvider` — funcionó en build/tests, pero el alta de cuenta en mapbox.com le pidió al usuario una **tarjeta de pago**, inaceptable para el proyecto.
  - Ante esto el usuario pidió directamente reemplazar todo el objeto DevExpress por `GMapControl` de GMap.NET, con un ejemplo de código propio como referencia. `GMap.NET.WindowsForms` 1.7.5 restaura con warning NU1701 (paquete apuntado a .NET Framework, no a `net10.0-windows`) — el build compila igual, es solo advertencia.
  - Se eliminó por completo el paquete `DevExpress.Win.Map`, `MapboxOptions.cs` (`FrontOne.Shared/Configuration`), la sección `"Mapbox"` de `appsettings.json`, y el parámetro `mapboxAccessToken`/`IOptions<MapboxOptions>` que viajaba desde `Program.cs` → `MainForm` → `HuertaEditarForm`.
  - **Trampa de versión ya resuelta**: NO agregar el paquete `GMap.NET.Core` por separado (aunque parezca el paquete "correcto" para los tipos `PointLatLng`/`GMaps`/`AccessMode`). `GMap.NET.WindowsForms` 1.7.5 **bundlea su propia copia** de `GMap.NET.Core.dll` (carpeta `lib/net40` del propio nupkg, sin declararla como dependencia NuGet) — si además se referencia el paquete `GMap.NET.Core` (ej. 2.1.7) por separado, quedan dos DLLs `GMap.NET.Core.dll` distintas compitiendo por el mismo nombre en el bin, y la que gana la copia final (la vieja, bundleada, versión de ensamblado `2.1.6.0`) no coincide en layout con la que usó el compilador → `TypeLoadException: Could not load type 'GMap.NET.Singleton\`1'` al iniciar el form. Solución: referenciar **solo** `GMap.NET.WindowsForms` en el `.csproj`; los tipos de `GMap.NET.Core` llegan igual porque viven en la misma carpeta `lib/net40` del paquete y NuGet los expone juntos.
  - **Dependencia oculta ya resuelta — `System.Data.SQLite`**: el constructor estático (`.cctor`) de `GMapControl` crea internamente una `GMap.NET.CacheProviders.SQLitePureImageCache` (su caché local de tiles en disco) — esto ocurre **siempre**, sin importar que `GMaps.Instance.Mode = AccessMode.ServerOnly` (ese modo solo evita usar la caché, no evita que se intente crear el objeto). Sin el ensamblado `System.Data.SQLite` en el proyecto, esto revienta con `TypeInitializationException` → `FileNotFoundException: Could not load file or assembly 'System.Data.SQLite, Version=1.0.98.0...'` al primer `new GMapControl()`. Solución: agregar `<PackageReference Include="System.Data.SQLite.Core" Version="1.0.119" />` al `.csproj` de `FrontOne.WinForms` — trae el DLL managed más los binarios nativos (`runtimes/win-x64/native/SQLite.Interop.dll` y `win-x86`), que .NET resuelve solo según la arquitectura del proceso en tiempo de ejecución. No hace falta configurar nada más (no se usa la BD de caché SQLite realmente por el `ServerOnly`, pero el ensamblado tiene que estar presente para que el tipo cargue).
- Proveedor de tiles: `GMapProviders.GoogleHybridMap` (satélite + calles/etiquetas de Google), sin necesidad de API Key — scrapea los tile servers de Google directamente. **Mismo tipo de riesgo de bloqueo que tuvo OpenStreetMap** (no es un uso oficial/soportado por Google), no verificado aún en uso prolongado; si llega a bloquearse, las alternativas ya wireadas en `BtnRecargarMapa_Click` (si se agrega, ver ejemplo del usuario) son `GoogleSatelliteMap`, `GoogleMap` u `OpenCycleMap`.
- Pin: un único `GMapOverlay` (`_mapOverlayHuerta`) agregado una sola vez a `_mapHuerta.Overlays` en `InicializarMapa()`; el marcador es un `GMarkerGoogle` que se limpia (`_mapOverlayHuerta.Markers.Clear()`) y se vuelve a crear en cada llamada a `ActualizarMapaUbicacion()`, con tooltip siempre visible (`MarkerTooltipMode.Always`) mostrando nombre/latitud/longitud.
  - **`GMarkerGoogleType.*` (íconos predefinidos, ej. `blue_pushpin`) NO se pueden usar, definitivo**: su bitmap se carga desde un `.resources` embebido viejo dentro de `GMap.NET.WindowsForms.dll`, y eso requiere `BinaryFormatter`. Se probó reactivar el switch de compatibilidad `<EnableUnsafeBinaryFormatterSerialization>true</EnableUnsafeBinaryFormatterSerialization>` (`.csproj`) pero **no sirve en esta versión de .NET** — el error cambia de `NotSupportedException: ... are disabled` (deshabilitado, activable con el switch) a `PlatformNotSupportedException: ... have been removed` (eliminado del runtime, el switch ya no tiene código que reactivar). Se quitó el switch del `.csproj` por inútil.
  - **Solución definitiva**: ícono PNG propio, embebido en el proyecto (no en `GMap.NET.WindowsForms.dll`, así que no toca el recurso viejo con `BinaryFormatter`). Archivo `FrontOne.WinForms/Resources/Mapas/PinHuerta.png` (64×64, provisto por el usuario), registrado en el `.csproj` como `<EmbeddedResource Include="Resources\Mapas\PinHuerta.png" />` (con su `<None Remove>` correspondiente, patrón estándar para sacar un archivo del glob implícito `None` y pasarlo a `EmbeddedResource`). `CrearBitmapPin()` en el `.cs` lo carga vía `Assembly.GetExecutingAssembly().GetManifestResourceStream("FrontOne.WinForms.Resources.Mapas.PinHuerta.png")` (nombre lógico = `{RootNamespace}.{RutaConPuntos}`, verificado con `GetManifestResourceNames()`) y `new Bitmap(stream)`. Pasado al constructor `GMarkerGoogle(PointLatLng, Bitmap)` (no al de `GMarkerGoogleType`, que es el que dispara el recurso embebido de la librería). `marcador.Offset = new Point(-iconoPin.Width/2, -iconoPin.Height)`, calculado del tamaño real del bitmap cargado (no hardcodeado), para que la punta del pin quede sobre la coordenada.
    - Si se cambia el ícono a futuro, solo hay que reemplazar el archivo `PinHuerta.png` (mismo nombre/ruta) — no hace falta tocar código. Si cambia de nombre/ruta, actualizar la constante `RecursoIconoPin` en `HuertaEditarForm.cs` y el `Include` del `.csproj`.
    - (Antes de tener el PNG del usuario, se usó temporalmente un pin dibujado a mano con GDI+/`GraphicsPath` como alternativa sin `BinaryFormatter` — reemplazado por completo por el PNG.)
- `ActualizarMapaUbicacion()` en el `.cs`: si Latitud **o** Longitud está en 0 (falta capturar cualquiera de las dos — condición `||`, no `&&`, para no pintar con datos a medias mientras el usuario todavía está tecleando), limpia el overlay (sin pin); si ambas están capturadas, agrega el marcador en ese `PointLatLng` y centra+hace zoom (`_mapHuerta.Position` / `.Zoom = 14`) el mapa ahí. Se llama: (1) en vivo, wireado a `_spnLatitud.EditValueChanged`/`_spnLongitud.EditValueChanged`; (2) al cargar una huerta existente desde el `DataNavigator`; (3) al limpiar el formulario (Nuevo).
- Centro/zoom por defecto (sin huerta cargada): centro geográfico de México (`23.6345, -102.5528`), zoom `5` — solo referencia visual inicial, no tiene significado de negocio. `GMaps.Instance.Mode = AccessMode.ServerOnly` fijado en `InicializarMapa()`.
- `GMapControl` no implementa `ISupportInitialize` (a diferencia de los editores DevExpress) — no lleva `BeginInit()/EndInit()` alrededor de su instanciación en `InitializeComponent()`.
- **Barra de controles en `panelControl3`** (encima del mapa, agregada por el usuario directamente en el diseñador de VS replicando su ejemplo de referencia original): `chk_mostrar` (`CheckEdit`, caption "Mostrar Coordenada") + `comboBoxEdit1` (`ComboBoxEdit` con items `"Google Maps Satélite"/"Google Maps Callejero"/"Google Maps Híbrido"/"OpenClycleMap"`, `SelectedIndex = 2` por defecto) + `btRecargarMapa` (`SimpleButton` "Recargar Mapas"). Wireado en el `.cs`:
  - `ChkMostrar_CheckedChanged` → llama `ActualizarMapaUbicacion()` de nuevo; el tooltip del pin muestra lat/long solo si `chk_mostrar.Checked` es `true`, si no solo el nombre de la huerta.
  - `BtRecargarMapa_Click` → cambia `_mapHuerta.MapProvider` según el texto seleccionado en `comboBoxEdit1` (switch expression) y llama `_mapHuerta.Refresh()`.

## Decisiones de UI ya tomadas (no volver a preguntar)

- **Ribbon de `MainForm`**: 3 pestañas por módulo — **Catálogos** (grupos "Ubicaciones": Países/Estados; "Socios de Negocio": Productores/Huertas), **Seguridad** (grupo "Usuarios y Roles": Usuarios/Roles/Permisos), **Sistema** (grupos "Configuración": Conexiones; "Aplicación": Salir). Botones en estilo `RibbonItemStyles.Large` (ícono arriba, texto abajo).
- **MDI con pestañas**: `MainForm` usa `DevExpress.XtraTabbedMdi.XtraTabbedMdiManager` — los forms MDI-child (Productores, Huertas) se muestran como pestañas de documento arriba, no como ventanas flotantes.
- **Flujo de catálogos vía lookupedit (regla fija)**: el botón "+" (quick-add) de un `LookUpEdit` **no** abre directo el form de alta — abre el **listado** del catálogo (`{EntidadPlural}Form`, con Nuevo/Editar/Eliminar/Cerrar), para poder editar y borrar desde ahí también, no solo crear. Excepción: Productor, cuyo "+" abre `ProductorEditarForm` directo porque ese form YA es maestro-detalle completo (navigator + Nuevo/Eliminar/Guardar), abrir el picker ahí sería un downgrade.
- **Todo `LookUpEdit` del proyecto** (regla dura, ver `CLAUDE.md`): `Properties.NullText = "Seleccionar"` siempre; si tiene botón custom (`Plus`, etc.) hay que agregar explícitamente `ButtonPredefines.Combo` antes, porque DevExpress oculta la flecha automática en cuanto agregás cualquier botón a `Properties.Buttons`.
- **Íconos de botones CRUD** (regla dura, ver `CLAUDE.md`): todo `_btnNuevo`/`_btnEditar`/`_btnEliminar`/`_btnCerrar` usa el mismo ícono en todo el proyecto, tomado de `FrontOne.WinForms/Forms/Catalogos/EstadosForm.resx`; todo `_btnGuardar`/`_btnCancelar` (de cualquier `{Entidad}EditarForm`, incluidos los maestro-detalle) usa el ícono de `FrontOne.WinForms/Forms/Catalogos/ProductoEditarForm.resx` — son dos fuentes distintas, no confundir. Los `.resx` de DevExpress son XML de texto plano (bitmap en base64), así que se pueden copiar los bloques `<data>` a mano sin abrir Visual Studio — el `.resx` tiene que vivir en la misma carpeta/namespace que su `.cs` o `resources.GetObject(...)` no encuentra el ícono en runtime.
- **Estructura de carpetas de `Forms/`**: subcarpetas por módulo — `Forms/Seguridad`, `Forms/Catalogos`, `Forms/Sistema` (cada una con su propio namespace `FrontOne.WinForms.Forms.{Carpeta}`). `MainForm` se queda en la raíz de `Forms/` por ser el shell de la app, no pertenece a ningún módulo.
- **Orden de botones** (regla dura, ver `CLAUDE.md`): en los forms maestro-detalle (`ProductorEditarForm`/`HuertaEditarForm`) el grupo izquierdo va **Nuevo, Guardar, Eliminar** en ese orden (los 3 con `Anchor = Bottom, Left`), y `Cancelar` siempre solo a la derecha (`Bottom, Right`). Mismo criterio en los listados: Nuevo/Editar/Eliminar a la izquierda, Cerrar a la derecha.

## Patrones de código establecidos (repetir en todo módulo nuevo)

- **Patrón clásico VS Designer** en todo `XtraForm`: `{Form}.Designer.cs` (parcial, controles como campos privados, `InitializeComponent()`) + `{Form}.cs` (ctor vacío para el diseñador + ctor con servicios inyectados `: this()`). Nunca lambdas inline en `Designer.cs` — rompe el diseñador de VS.
- **Maestro-detalle con `DataNavigator`**: `BindingSource` sobre `List<TDto>` cacheada, `CurrentChanged` recarga el form, "Nuevo" limpia campos sin tocar la posición del navigator, "Guardar" inserta/actualiza y reposiciona.
- **Auditoría obligatoria**: todo servicio Application con Crear/Actualizar/Eliminar inyecta `AuditService` + `ICurrentUserProvider`, relee antes/después, serializa a JSON completo (no diff campo por campo).
- **Todo módulo nuevo repite**: Entidad → DTO → Interfaz repo → Repositorio (`SqlRepositoryBase`) → SPs (`{Schema}.sp_{Entidad}_{Accion}`) → Servicio (con auditoría) → Validador → Form(s) (listado + editar, ambos con íconos e patrón clásico).
- **Permiso "quick-add" en lookups**: antes de abrir el listado/editor de un catálogo relacionado desde un "+", se valida `SessionContext.TienePermiso(modulo, pantalla, "Crear")`; si no tiene, `XtraMessageBox` de advertencia y no abre nada.

## Idioma: comentarios y mensajes al usuario (regla dura, ver `CLAUDE.md`)

Todo comentario de código (`//`, `/* */`, `///`, comentarios `.sql`) y todo mensaje visible para el usuario (`XtraMessageBox`, mensajes de excepción que llegan a UI, `Text`/`Caption`/`NullText`) va en **español**. Se hizo un barrido inicial sobre el código existente (el proyecto ya estaba mayormente en español; se corrigieron los pocos textos sueltos en inglés: "Password:" → "Contraseña:" en `ProductorEditarForm`/`UsuarioEditarForm`, "Status" → "Estatus" en el módulo de Huertas, y un comentario en `003_Seed_Manager.sql`). Cualquier cosa nueva que se agregue de acá en adelante debe nacer en español, no traducirse después.

**Nota de nomenclatura fijada en este barrido**: el campo de estado de vida de una huerta (catálogo `StatusHuerta`, valores tipo Nueva/Producción/etc.) se etiqueta en UI como **"Estatus"**, no "Estado" — porque el mismo form ya tiene un campo "Estado:" para el estado geográfico (`Catalogos.Estado`, ligado a País). Usar "Estado" para ambos generaba colisión visual. De paso se corrigió `_lblEstatusActivo` (el combo Activa/Baja) que estaba mal etiquetado como "Estado:" → ahora dice "Activo:". Los nombres de clase/tabla (`StatusHuerta`, `StatusHuertaService`, etc.) NO se tocaron — es solo el texto visible en pantalla el que cambió.

ABR-OCT.2026`) a la BD `FrontOne` de desarrollo: **33,190 productores** y **54,137 huertas**, todas de Michoacán de Ocampo (EstadoId 16). Script registrado en `Database/Catalogos/020_Import_Excel_Huertas_Productores.sql` (staging temporal + `BULK INSERT` desde TSVs generados con Python/pandas — los TSVs eran temporales de la sesión, ya no existen; el script tiene guardas para NO re-ejecutarse si las tablas tienen datos).

Decisiones acordadas con el usuario:
- **Cartilla del Excel: ignorada** (no es derivable del SAGARPA — solo coincide en ~39k de 54k filas — y no hay campo destino; si se necesita después, habría que re-extraerla del Excel).
- **Domicilio del productor** (Población/Municipio/Estado): el de su **primera huerta** en el archivo (1,400 productores tienen huertas en >1 población).
- **Clave del productor**: secuencial `000001`..`033190` en orden de aparición en el archivo.
- **Nombre del productor normalizado** al importar: espacios múltiples/tabs colapsados a uno y sin espacios en extremos — el Excel traía ~506 filas con el mismo productor escrito con espacios extra (o distinta capitalización), que la colación CI de SQL habría colisionado en el join (de hecho la primera corrida falló por SAGARPA duplicado por esto; se corrigió deduplicando case-insensitive en Python).
- Mapeo Huerta: Huerta→Nombre, Poblacion→PoblacionId (match insensible a acentos/mayúsculas contra `Catalogos.Poblacion`, las 46 ya existían del seed), Municipio→Municipio (texto), SAGARPA→RegistroSagarpa (54,137 únicos ✓), Superficie→Superficie, AlturaNivelMar→Altura, Latitud/Longitud→Latitud/Longitud, Activo=1, GlobalGap=0, resto NULL.

**Rendimiento post-importación (ya corregido en parte)**: tras la importación aparecieron timeouts (`Win32Exception: Tiempo de espera... agotado` en `sp_Productor_Obtener`) y pickers vacíos sin columnas. Causa: `ProductorEditarForm.CargarHuertasDelProductorAsync` bajaba las 54k huertas y filtraba client-side EN CADA navegación del `DataNavigator`, y los pickers (`HuertasForm`/`ProductoresForm`) cargaban todo el catálogo al abrir con columnas auto-pobladas (sin datos = sin columnas). Fix aplicado (`Database/Catalogos/021_SP_Huerta_Productor_Busqueda.sql` + capas):
- `sp_Huerta_Obtener` ahora acepta `@ProductorId` (filtro server-side, ~26ms); `HuertaService.ObtenerPorProductorAsync` lo usa desde `ProductorEditarForm`.
- Pickers rehechos como **búsqueda server-side**: `sp_Huerta_Buscar`/`sp_Productor_Buscar` (`@Filtro` LIKE sobre nombre/SAGARPA/clave, `TOP 500`, ~1.3s), mínimo 2 caracteres, Enter o botón Buscar, columnas explícitas (`GridColumn`), ya NO cargan nada al abrir. `HuertasForm.HuertaSeleccionada` cambió de tipo `HuertaDto` a `HuertaBusquedaDto` (DTO ligero nuevo en `Domain/DTOs`).
- `HuertaEditarForm` recibió el mismo tratamiento: ya NO carga las 54k huertas ni los 33k productores al abrir. El form abre vacío (solo catálogos chicos); el `DataNavigator` contiene **solo las huertas del productor en contexto** (`CargarHuertasDelProductorAsync`, filtro server-side). La lupa de `_txtNombreHuerta` abre el picker de búsqueda y al elegir carga las huertas del productor de esa huerta, posicionando en ella. `_cmbProductor` dejó de ser `LookUpEdit` con catálogo completo — ahora es `ButtonEdit` de solo lectura con botones Search (abre `ProductoresForm` picker) y Plus (alta rápida, sin recarga posterior); el id vive en `_productorSeleccionadoId` y el nombre se resuelve vía `ProductorService.ObtenerPorIdAsync` (nuevo) con caché en memoria (`_nombresProductorCache`). Guardar/Eliminar recargan solo las huertas del productor.

## Jerarquía geográfica completa: País → Estado → Municipio → Población (jul 2026)

Se agregó **Catalogos.Municipio** como nivel intermedio real entre Estado y Población (antes `Poblacion` colgaba directo de `Estado`, y sus 238 registros eran en realidad municipios; Huerta/Productor guardaban la localidad como texto libre en una columna `Municipio`). El usuario pidió esto explícitamente y dio dos catálogos de INEGI (`Michoacan.xlsx`, `Jalisco.xlsx`, columnas `CVE_ENT/Estado/CVE_MUN/Municipio/CVE_LOC/Poblacion`) para poblar el nuevo nivel.

**Migración de datos** (`Database/Catalogos/022_Schema_Municipio_Migracion.sql`, ya ejecutada):
- Los 238 `Poblacion` viejos (= municipios) pasaron a `Catalogos.Municipio`.
- Import INEGI: 238 municipios (ya cubiertos, matcheados 1:1) + 28,652 localidades nuevas en `Poblacion` (ahora con `MunicipioId NOT NULL`, ya no `EstadoId`).
- Las 54,137 huertas y 33,190 productores se remapearon: `PoblacionId` viejo (que apuntaba al municipio) → `MunicipioId`; el texto libre `Municipio`/localidad → nuevo `PoblacionId` (match sin acentos/mayúsculas contra INEGI; **907 localidades de huertas no estaban en INEGI** y se insertaron como `Poblacion` nuevas bajo su municipio — 0 en productores porque comparten domicilio con sus huertas).
- Columnas `Huerta.Municipio`/`Productor.Municipio` (texto) eliminadas; ambas tablas ganaron `MunicipioId INT NULL` con FK a `Catalogos.Municipio`.
- Índice único de Población cambió de `(Nombre, EstadoId)` a `(Nombre, MunicipioId)` — INEGI trae localidades con el mismo nombre en distintos municipios del mismo estado (ej. "Acaspoles" en Jalisco), cosa que el índice viejo no permitía.
- **Bug de importación anterior descubierto y corregido en el camino**: los 33,190 `Productor.Municipio` traían un `CHAR(13)` (retorno de carro) pegado al final — el TSV del import de julio (`020_...sql`) se generó con `pandas.to_csv` sin `lineterminator="\n"` explícito, y como `Municipio` era el ÚLTIMO campo de esa fila, el `\r` de la línea CRLF quedó pegado al valor (invisible, `LEN()` lo delataba). Se limpió con `REPLACE(Municipio, CHAR(13), '')` como parte de la migración, antes de usar ese texto para el match contra INEGI. **Lección para futuros imports por TSV/BULK INSERT**: siempre generar los TSV con `lineterminator="\n"` en pandas, o el último campo de cada fila queda contaminado con `\r` si `ROWTERMINATOR` del `BULK INSERT` es `'0x0a'` (solo LF).
- SQL Server resuelve nombres de **columna** en tiempo de compilación de todo el batch (a diferencia de nombres de **tabla**, que sí son diferidos) — un `ALTER TABLE ADD columna` seguido de una referencia a esa columna en el mismo batch (sin `GO` de por medio) truena con "Invalid column name" aunque el `ALTER` esté antes en el texto. Solución usada: cada `ALTER TABLE ADD` en su propio batch (`GO`), con `SET XACT_ABORT ON` (en vez de `TRY/CATCH`, que no puede cruzar `GO`) para mantener atomicidad — rollback automático ante cualquier error en la transacción abierta.

**Capas y UI** (`023_SP_Municipio_Poblacion_Huerta_Productor.sql` + capas C# + forms):
- Módulo `Municipio` nuevo completo: `Entidad`/`MunicipioDto`/`IMunicipioRepository`/`MunicipioRepository`/`MunicipioService` (con auditoría, mismo patrón que `EstadoService` — valida que el Estado exista al crear/editar), SPs `sp_Municipio_Obtener(@EstadoId,@Id)/_Insertar/_Actualizar/_Eliminar`, `MunicipiosForm` (listado, filtro País→Estado en cascada, igual patrón que `EstadosForm`) + `MunicipioEditarForm` (País→Estado→Nombre→Activo, sin Clave — Municipio no tiene clave corta como Estado). Pantalla nueva en Ribbon (`_btnMunicipios`, grupo "Ubicaciones" junto a Países/Estados) y permiso seed (`Seguridad/010_Seed_Pantalla_Municipios.sql`, solo rol Administrador por default, igual que los demás catálogos).
- `Poblacion`: `EstadoId int?` → `MunicipioId int` (ya no nullable). `sp_Poblacion_Obtener/_Insertar/_Actualizar` ahora reciben `@MunicipioId`. `PoblacionesForm` ganó cascada de 3 niveles (País→Estado→Municipio) para filtrar/dar de alta, `PoblacionEditarForm` igual (el combo Municipio se agregó entre Estado y Nombre).
- `Huerta`/`Productor`: columna texto `Municipio` → `MunicipioId int?` (entidad, DTO, SPs, repos, servicios). **Orden de campos fijado por el usuario, sin excepción: País → Estado → Municipio → Población** en `HuertaEditarForm` y `ProductorEditarForm` (antes era País→Estado→Población→Municipio-texto). `_cmbMunicipio` es `LookUpEdit` cascada de `_cmbEstado`, con botón "+" que abre `MunicipiosForm`; `_cmbPoblacion` ahora cascada de `_cmbMunicipio` (ya no de `_cmbEstado`). El grid de huertas del productor (`ProductorEditarForm`, columna "Municipio") ahora resuelve el nombre vía diccionario `MunicipioService.ObtenerAsync()` en vez de leer texto libre.
- Pickers de búsqueda (`sp_Huerta_Buscar`/`sp_Productor_Buscar`) no tocan `Municipio`, sin cambios ahí.

Build 0 errores, tests 2/2. **Pendiente de probar en vivo por el usuario**: cascada completa en ambos forms, alta rápida de Municipio desde el botón "+", y que el grid de huertas del productor muestre bien el municipio.

## Navegación de `HuertaEditarForm`: DataNavigator reemplazado por 4 botones planos (jul 2026)

El `DataNavigator` de DevExpress se quitó por completo de `HuertaEditarForm` — el usuario pidió navegar el catálogo COMPLETO (Id de creación, sin importar productor) sin cargar nada a memoria, ya que el `DataNavigator` estaba atado a un `BindingSource` con solo las huertas del productor en pantalla (ver sección de rendimiento arriba). Reemplazado por 4 `SimpleButton` normales (`_btnInicio`/`_btnAnterior`/`_btnSiguiente`/`_btnFin`, donde antes estaba el navigator, misma posición) que llaman 4 SPs nuevos vía **keyset/seek pagination** — cada click es un `TOP 1 ... WHERE Id >/< @Id ORDER BY Id` (índice de la PK, O(log n), no un recorrido), nunca materializa la tabla completa. Se probó con 54k+ huertas reales: <20ms por navegación.

**Comportamiento exacto** (decidido con el usuario, aplica solo a Huerta por ahora — si funciona bien se replica al resto de los forms con navegador):
- **Inicio**: siempre carga el primer registro de toda la BD (`Id` más chico) — `sp_Huerta_ObtenerPrimero`.
- **Fin**: siempre el último (`Id` más grande) — `sp_Huerta_ObtenerUltimo`.
- **Anterior**: si no hay nada cargado (`_huertaActual == null`), **no hace nada**. Si hay, busca el registro con `Id` inmediato menor — `sp_Huerta_ObtenerAnterior(@Id)`.
- **Siguiente**: si no hay nada cargado, actúa como Inicio (toma el primero). Si hay, busca el `Id` inmediato mayor — `sp_Huerta_ObtenerSiguiente(@Id)`.
- En los extremos (ya en el primero y das Anterior, o en el último y das Siguiente): el SP no regresa fila, el botón **no hace nada** (sin aviso — así se decidió, más simple).
- **Después de Eliminar**: el formulario queda en blanco (`LimpiarFormulario()`), no se autocarga nada — hay que buscar de nuevo con la lupa o usar Inicio/Fin.
- Se explícitamente decidió **no** mostrar "registro X de Y" (costaría una consulta de conteo extra por cada navegación) — si hace falta más adelante, se agrega aparte.

Orden de navegación = **Id de creación** (no alfabético por Nombre) — decisión explícita del usuario, más simple y sin ambigüedad de desempate. `sp_Huerta_Obtener`/`sp_Huerta_Buscar` (listas/pickers) siguen ordenando por Nombre como antes, sin cambios — esto solo afecta el orden de Inicio/Anterior/Siguiente/Fin.

Como consecuencia, **desapareció por completo** el concepto de "huertas del productor en el navegador": ya no existe `_huertasBindingSource` ni `CargarHuertasDelProductorAsync` en `HuertaEditarForm`. La lupa de búsqueda, Guardar y el propio Nuevo ahora simplemente cargan/limpian **un solo registro** (`HuertaService.ObtenerPorIdAsync` nuevo) — el estado del form es nada más `_huertaActual`. El label `_lblIdHuerta` (agregado en el paso anterior) sigue mostrando el Id del registro cargado para confirmar visualmente la navegación.

SQL nuevo: `Database/Catalogos/024_SP_Huerta_Navegacion.sql` (`sp_Huerta_ObtenerPrimero/Ultimo/Siguiente/Anterior`), ya ejecutado — no necesitó índice nuevo porque `Id` ya es la PK/clustered.

**Íconos**: los 4 botones son solo ícono (28×23, sin texto) + `ToolTip` nativo de DevExpress (`SimpleButton.ToolTip`, string plano) mostrando "Inicio"/"Anterior"/"Siguiente"/"Fin" al pasar el mouse. Los íconos (flechas simples con/sin barra) se dibujan por código con GDI+ en tiempo de ejecución (`CrearIconoFlecha`, 16×16, `Color.CornflowerBlue`, antialiased) — no se descargan de internet ni se usan archivos externos, para no depender de licencias de terceros (mismo criterio que `CrearBitmapPin` del mapa). Asignados en el constructor sin parámetros (`AsignarIconosNavegacion()`), así se ven incluso si algo instancia el form sin DI.

**Validado y replicado (jul 2026)**: el usuario probó Huertas y aprobó (íconos + tooltip). Se replicó **exactamente el mismo patrón** en `ProductorEditarForm`, el único otro form con `DataNavigator` en todo el proyecto (era el único caso restante — se verificó con `grep -rl "DataNavigator"` sobre `FrontOne.WinForms/Forms`). Este form tenía además el mismo problema de fondo que Huertas: `RecargarListaProductoresAsync()` bajaba **los 33,190 productores completos** a memoria en cada apertura/guardado solo para alimentar su propio `DataNavigator` — el cambio lo elimina de raíz también aquí, no solo agrega los botones.

- SQL nuevo: `Database/Catalogos/025_SP_Productor_Navegacion.sql` (`sp_Productor_ObtenerPrimero/Ultimo/Siguiente/Anterior`), mismo criterio por `Id` de creación, ya ejecutado y probado (10ms).
- `IProductorRepository`/`ProductorRepository`/`ProductorService` ganaron los mismos 4 métodos de navegación que Huerta (`ProductorService.ObtenerPorIdAsync` ya existía de antes, se reutiliza para la lupa/Guardar).

## Módulo "Lista de Precio Fruta" (primer módulo operativo, primer consumo de SAP desde Application)

Primer módulo de negocio real (no catálogo) y primera vez que `FrontOne.Application` consume SAP Business One. Requerimiento del usuario: traer de SAP (Service Layer) únicamente `ItemCode`/`ItemName` de los items cuyo código inicia con `MP` (fruta), capturar a mano en FrontOne tres listas de precio (Lista 1/2/3) y guardarlas con una vigencia por fecha única o por rango, bloqueando el guardado si la vigencia se traslapa con una ya existente para el mismo `ItemCode`.

**Brecha de arquitectura resuelta**: hasta ahora `FrontOne.Application` solo dependía de `FrontOne.Domain`+`FrontOne.Shared` (nunca de Infrastructure), y `ISapServiceLayerClient` vive en `FrontOne.Infrastructure.SapB1`. Para no romper esa regla se agregó `Domain.Interfaces.ISapItemRepository` (análogo a `IHuertaRepository` pero para SAP), implementado en `Infrastructure.SapB1.Repositories.SapItemRepository` (consume `ISapServiceLayerClient.GetAsync<T>` con `Items?$filter=startswith(ItemCode,'MP')&$select=ItemCode,ItemName`, deserializa el envelope OData `{"value":[...]}` vía `Models/SapItemsResponse.cs`). `Application` sigue sin referenciar ningún proyecto de Infrastructure — solo ve la interfaz de Domain.

**Nuevo schema `Acopio`** (primer schema de negocio, no catálogo): `Database/Acopio/001_Schema_ListaPrecioFruta.sql` (tabla `Acopio.ListaPrecioFruta`: ItemCode, ItemName, Lista1/2/3 `DECIMAL(18,4)`, FechaInicio `DATE`, FechaFin `DATE NULL`, Activo, `CHECK` FechaFin>=FechaInicio) + `002_SP_ListaPrecioFruta.sql` (`sp_ListaPrecioFruta_Obtener/Insertar/ExisteTraslape`). El traslape se calcula tratando "sin rango" como un día único (`ISNULL(FechaFin, FechaInicio)`), condición clásica de intersección de intervalos: `FechaInicio <= ISNULL(@FechaFin,@FechaInicio) AND ISNULL(FechaFin,FechaInicio) >= @FechaInicio`. Probado a mano con sqlcmd: rango 16–20 jul choca con consulta del 18 jul (`Existe=1`) y no choca con el 1 ago (`Existe=0`).

`ListaPrecioFrutaService.GuardarListaAsync` valida traslape de **todas** las filas de la grilla antes de insertar cualquiera (si una sola choca, se rechaza el guardado completo con `ValidationException` listando los `ItemCode` en conflicto) — igual que el resto del guardado, no hay transacción SQL explícita porque cada fila es un INSERT independiente ya validado de antemano; se audita cada fila insertada por separado (`Modulo="Acopio"`, `TipoAccionAuditoria.Crear`).

`ListaPrecioFrutaForm` (`FrontOne.WinForms/Forms/Acopio/`, nueva carpeta): `CheckEdit` "Precios por rango" habilita/deshabilita el segundo `DateEdit` (si se desmarca, se limpia `_dtFechaFin.EditValue`); botón "Consultar SAP" trae los items MP y llena un `GridControl` editable (`BindingList<FilaListaPrecioFruta>`, clase auxiliar nueva) — columnas ItemCode/ItemName (renombrada "Producto") de solo lectura, Lista 1/2/3 editables con formato numérico `n2`; botón Guardar arma un `ListaPrecioFrutaDto` por fila con la misma fecha/rango elegido y llama al service. Íconos de Guardar/Cerrar copiados igual que siempre (`ListaPrecioFrutaForm.resx` ensamblado a mano desde los bloques `<data>` de `ProductoEditarForm.resx`/`EstadosForm.resx`).

Nuevo módulo de seguridad **"Acopio"** (primer módulo aparte de Catálogos/Seguridad) con pantalla `ListaPrecioFruta` — `Database/Seguridad/011_Seed_Pantalla_ListaPrecioFruta.sql`. `MainForm` ganó una `RibbonPage` "Acopio" nueva con el grupo "Precios de Fruta" y el botón correspondiente (`MaxItemId` subió a 12).

**Conectividad SAP resuelta (2026-07-16)**: el `CompanyDb` original (`TEST_PROD_FASA`) daba `-8012 Company version mismatch` al hacer login — problema de esa base específica, no de la app. El usuario entregó credenciales nuevas apuntando a `FRONTERRA_PROTO` (misma URL, mismo usuario `manager`, mismo password `Fterra@1234` — solo cambió la base). Se probó en vivo por `curl`: login OK (200) y `GET Items?$filter=startswith(ItemCode,'MP')&$select=ItemCode,ItemName` regresa exactamente el shape esperado (`{"value":[{"ItemCode":"MP-00008","ItemName":"EXP CAL 96 CAT 1"},...]}`, con `odata.etag` extra por fila que se ignora sin problema al deserializar). `appsettings.json` actualizado (`Sap.CompanyDb` = `FRONTERRA_PROTO`; el password cifrado no cambió porque el password en sí no cambió). ### Bug preexistente encontrado y corregido: `SapServiceLayerClient` mandaba JSON en camelCase, SAP exige PascalCase

Al probar "Consultar SAP" en vivo el usuario recibió `{"code":206,"message":"Invalid login credential."}` a pesar de que las credenciales eran correctas (confirmado por `curl` directo con el mismo `CompanyDB`/`UserName`/`Password`). Causa raíz: `SapServiceLayerClient.cs` usaba un único `JsonSerializerOptions` con `JsonSerializerDefaults.Web` para **todo** (leer y escribir), y esos defaults fuerzan `PropertyNamingPolicy = CamelCase` al serializar. El payload de `Login` se arma como objeto anónimo con propiedades `CompanyDB`/`UserName`/`Password` (PascalCase, como las espera el Service Layer), pero al serializar salían como `companyDB`/`userName`/`password` — Service Layer los rechaza como credencial inválida en vez de error de parseo. Reproducido y confirmado con `curl` mandando el body en camelCase: mismo error exacto que reportó el usuario.

Este bug es preexistente (no lo introdujo el módulo Lista de Precio Fruta) y llevaba tiempo enmascarado: la `CompanyDb` vieja (`TEST_PROD_FASA`) fallaba antes por "Company version mismatch" (error de esa base específica), así que el login nunca llegaba a la etapa de validar credenciales donde el bug de camelCase se manifiesta. Al cambiar a `FRONTERRA_PROTO` (que sí es una base sana) fue la primera vez que el login llegó lo bastante lejos como para exponerlo. También afectaba potencialmente cualquier `POST`/`PATCH` a entidades de SAP (Órdenes, Facturas, etc. — todas con campos PascalCase como `CardCode`/`ItemCode`), aunque el único código existente que hace peticiones de escritura hoy es el propio login.

**Fix**: se separó en dos `JsonSerializerOptions` estáticos — `ReadOptions` (los defaults de Web, sirven para deserializar respuestas de SAP porque el matching de nombres es insensible a mayúsculas) y `WriteOptions` (mismos defaults pero con `PropertyNamingPolicy = null`, para serializar cualquier body saliente respetando el PascalCase exacto que espera Service Layer). Se actualizaron los 4 usos: `SendOnceAsync` (bodies de `PostAsync`/`PatchAsync`), `LoginAsync` (payload de login), `ReadContentAsync` (deserializar respuestas) y `BuildBatchBody` (bodies dentro de `$batch`). Verificado con `curl` (login PascalCase → 200 OK; camelCase → mismo error 206 que veía el usuario) y con build+tests limpios tras el cambio.

**Nota aparte**: la contraseña SQL guardada en memoria para el login `sa` (`Fr0nt3rr42026/*-+`) ya no funciona ("Login failed") — se usó autenticación Windows integrada (`sqlcmd -S LIDER-TI -d FrontOne -E -C`) para desplegar este módulo. Si se necesita `sa` de nuevo, pedir al usuario que confirme/actualice la contraseña.

### Script de utilidad: reinicio de IDENTITY solo en tablas vacías

El usuario notó que `Moneda` arrancaba en Id 4/5 en vez de 1/2 (residuo de inserts/deletes de prueba durante el desarrollo) y pidió "un query que reinicie todos los Id de todas las tablas a 1". Explícitamente **no** se puede hacer eso de forma general: cualquier tabla con filas existentes (Productor 33,190 filas, Huerta 54,137, Poblacion 29,559, Pais/Estado/Municipio con datos reales, TipoPago/TipoCorte con catálogo real, ListaPrecioFruta con 920 filas de capturas reales del usuario, etc.) rompería FKs o chocaría de llave primaria si se reinicia el contador a 1 — el `RESEED` no renumera filas existentes, solo el próximo valor autogenerado.

Se creó `Database/Utilidades/Reseed_Identidades_Tablas_Vacias.sql` — recorre todas las tablas con columna `IDENTITY` del proyecto (vía `sys.identity_columns`), cuenta filas, y solo hace `DBCC CHECKIDENT (..., RESEED, 0)` en las que están **vacías**; el resto se reporta como "omitida (N filas existentes)" sin tocarlas. Es idempotente, se puede volver a correr cuando se quiera después de limpiar catálogos de prueba.

Al correrlo se detectó que `Acopio.Moneda` en realidad no estaba vacía — tenía justo las dos monedas de ejemplo del usuario (Pesos/MXN Id 4, Dólares Americanos/USD Id 5) que quedaron de una prueba anterior donde el `DELETE` de limpieza no se había ejecutado como se pensó. Como la tabla no tenía nada dependiendo de ellas todavía (`AcuerdoCorte` con 0 filas), se renumeraron a mano con `SET IDENTITY_INSERT ON` (borrar + reinsertar con Id explícito 1 y 2) en vez de perderlas, y se reseed el contador a 2. `AcuerdoCorte`, `TipoComercializacion` y `Variedad` sí estaban genuinamente vacías y quedaron reiniciadas a 1 por el script.

### Script de producción: `Inicializar_Datos_Produccion.sql`

Nuevo `Database/Utilidades/Inicializar_Datos_Produccion.sql` — para cuando se ponga la base en blanco en producción. Vacía (TRUNCATE) todas las tablas operativas de los módulos de pantallas (Catalogos.*, Acopio.*, Auditoria.Registro) y reinicia sus Id/folio para que el próximo registro arranque en 1 — incluye reiniciar `Acopio.SeqAcuerdoCorteFolio` a `0000001`. **`Seguridad.*` (Usuario, Rol, Permiso, UsuarioRol, Modulo, Pantalla, Accion) queda intacto a propósito** — la base recién puesta en blanco necesita seguir teniendo con qué iniciar sesión.

Técnica: como `TRUNCATE` exige que ninguna FK apunte a la tabla (en cualquier sentido), el script desactiva todas las FK del proyecto (`NOCHECK CONSTRAINT ALL`) antes de vaciar y las reactiva con `WITH CHECK CHECK CONSTRAINT ALL` al final — así no queda ninguna constraint deshabilitada. `TRUNCATE` además reinicia el `IDENTITY` al seed automáticamente, no hace falta `DBCC CHECKIDENT` aparte.

**No se ejecutó** contra la base de desarrollo (`Lider-TI\FrontOne`) — correrlo ahí habría borrado los 33,190 productores, 54,137 huertas y demás datos reales/de prueba que el usuario tiene cargados. Se validó solo la sintaxis con `SET PARSEONLY ON` (sin tocar datos) antes de guardarlo. Queda para ejecutarse manualmente, una sola vez, el día que se despliegue a producción.

**Regla para sesiones futuras**: cuando se hagan pruebas de INSERT/DELETE sobre tablas vacías durante el desarrollo, siempre dejar el Id/folio en 1 al terminar (no dejar residuos como pasó con `Acopio.Moneda` en la iteración anterior) — pedido explícito del usuario tras notar el folio arrancando en 4/5 por pruebas mal limpiadas.

**Regla dura nueva**: cada vez que se agregue un módulo/tabla nueva (operativa, no `Seguridad.*`), hay que sumarla también a `Database/Utilidades/Inicializar_Datos_Produccion.sql` (`@Tablas` + `RESTART` de su `SEQUENCE` si tiene folio) — documentado en `CLAUDE.md`.

## Módulo "Recepción de Fruta" (schema `Recepcion`, nuevo — página de Ribbon propia junto a Acopio)

## Cómo seguir trabajando en este proyecto (para cualquier sesión nueva de Claude)

1. Leer este archivo completo + `CLAUDE.md` antes de tocar código.
